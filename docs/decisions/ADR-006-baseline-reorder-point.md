# ADR-006: Add a reorder point to baseline B1

- **Status:** ACCEPTED (before any baseline result was produced, so no reported number changes)
- **Context:** The plant's static allergen ladder costs **29.5 h of changeover per weekly cycle (41% of the 72 h available)** with 7 allergen cleans when every SKU runs every week (computed from `configs/plant.yaml`). The first B1 version produced any SKU with even a small shortfall below its order-up-to level, so in practice it ran almost every SKU every week. No competent planner runs a 12-SKU allergen wheel weekly when cover allows a longer cycle. Comparing against that version would inflate the optimiser's changeover and capacity gains: the strawman the charter explicitly guards against.
- **Decision:** B1 becomes a standard (s, S) policy. It produces SKU p only if usable on-hand < forecast x `reorder_weeks` (s, default 1 week), and then up to forecast x (1 + `cover_weeks`) (S, default 2 weeks in total). With the defaults each SKU settles into a two-week cycle (tested: exactly 8 runs in 16 weeks at steady demand when capacity is not binding). The order and everything else are unchanged: MA(4) forecast, static allergen ladder, min/max run, pro-rata capacity repair, FEFO.
- **Consequences:** The baseline is stronger, so the optimiser's measured gains will be smaller and more credible. `reorder_weeks` and `cover_weeks` both join the fairness sweep (T5.2.1 frontier). A two-week cycle needs at least 2 weeks of saleable life; every SKU's max ship age is >= 1 week at MSL 50%, so product made in week t can serve t and t + 1.
- **Alternatives rejected:** fixed two-week rotation by family (rigid, ignores inventory); keeping the weekly wheel and noting it as a limitation (would make the headline result misleading).
